# 段階 B：SocketCAN と単輪立ち上げ

## 今回の実装範囲

`harurobo_base/can_monitor` は既に設定・起動された SocketCAN にバインドする。リンク設定やビットレート変更、アプリケーションからの CAN フレーム送信、駆動許可は行わない。CAN コントローラーは通常モードなら ACK などを返し得るので、電気的に受動で観測する場合はアダプターの listen-only 対応を確認する。

`/diagnostics` にインターフェース、受信カウンター、最後のデータ ID と経過時間を表示する。受信ソケットが開かなければ ERROR、データ無受信は STALE、直近の CAN エラーは WARN。観測した bus-off とソケット受信エラーは ERROR をプロセス再起動まで保持する。データ受信時の OK はバスに汎用フレームが流れているという意味であり、モーターの正常性や駆動許可を意味しない。未対応のモーター通信仕様を推定する用途には使わない。

## 未確定項目（次の実装に必要）

| 項目 | 記録する内容 |
|---|---|
| モーター／ドライバ | 本体と別体ドライバの有無・型番・ラベル、FW 版、該当版のマニュアルまたはメーカー資料 |
| USB-CAN | メーカー・型番、SocketCAN 対応、Classic/FD、listen-only 対応 |

| プロトコル | 指令・返信 ID、速度モード、符号と単位、データ形式、電流制限、応答周期、障害ビット |
| 停止 | 速度ゼロ・無効化の挙動、通信ウォッチドッグと設定値、ブレーキ／フリー、独立非常停止、駆動電源と保護 |

## 次の試験の順序

1. 仕様書を照合し、アダプター単体で Linux から型番と CAN IF を確認する。接続先で `lsusb`、`ip -details -statistics link show can0`。未確定の通信条件でインターフェースを起動しない。
2. 電源 OFF で配線・終端・停止手段を確認する。給電・単輪試験は担当者と確認後、車輪を浮かせ、低電流・低速度から実施する。
3. 仕様と受信記録を照合し、検証済みの単輪指令・停止・返信監視を追加する。通信断や PC 停止時の駆動側のローカル停止を計測する。床上走行前に独立停止手段を確認する。

段階 A の実機残件（右スティック中立と L1 保持再接続）は [段階 A 試験記録](stage-a-results.md) を参照。実装準備と実機の受入判定は分ける。

## 機器情報・資料照合（2026-11-20）

- ユーザー申告：別体ドライバ `DM3520-1EC`、FW 不明、変換器は DAMIAO 純正。モーター本体ラベルと変換器の実機 USB ID は未照合。
- [DM-S3519-1EC / DM3520-1EC メーカー取扱説明書（販売店ミラー、2024-11-18 表記）](https://cdn.shopify.com/s/files/1/0696/3832/4277/files/DM-S3519-1EC_User_Manual-1-1.pdf) を候補資料として照合。速度モードあり。資料上の速度は減速後の出力軸 `rad/s` であり、減速比を二重に掛けない。CAN は標準フレーム、出荷設定の記載は 1 Mbit/s、CAN FD にも対応するが実機の設定値は未確認。返信は対応する問い合わせに対して発生するため、受信だけで常時返信があると仮定しない。
- 同資料には起動時のシリアル表示に FW 版・ID・通信速度が含まれると記載されている。`TIMEOUT` 項目の存在だけでは安全停止を保証しない。実機で時間単位・設定値・通信断時の動作を確認する。資料内で一部レジスタ表記に不整合があり、FW と該当版資料が揃うまで設定書き込み・駆動フレーム送信を行わない。
- [DAMIAO 純正 USB-CAN の資料](https://damiao.enactic.ai/en/products/software/usb-can-conversion-software/) は CH340/CH341 の USB シリアルと、PC 側の 921600 baud を指定。この値はモーター側の CAN ビットレートではない。このタイプは既存の `can_monitor`（SocketCAN）に直接接続できる前提にしない。純正変換器は設定・確認用、走行系は実機の Classic CAN／CAN FD に合う SocketCAN 対応アダプターを第一候補とする。FW 書き換え、UART/CAN 配線変更はこの時点では行わない。

### 純正変換器の USB 単体確認

- USB ID `2e88:4603`、製品表示 `HDSC CDC Device`。Linux ドライバ `cdc_acm`、現デバイス `/dev/ttyACM0`、固定パス `/dev/serial/by-id/usb-HDSC_CDC_Device_00000000050C-if00`。`kaboc` は `dialout` に所属し、デバイスファイルの読み書き権限を確認した。
- 資料記載の CH340/CH341 とは異なる USB 実装で、接続後も SocketCAN インターフェースは生成されなかった。USB 認識だけを確認し、シリアルポートは開いていない。変換器の版・PC 側シリアルのフレーム形式・CAN FD 対応は未確定。

### DM-USBCU1 公開仕様との照合

- [DM-USBCU1 製品ページ](https://damiao.enactic.ai/products/hardware/dm-usbcu1) はモジュール V3.0 と USB シリアル用フレーム仕様 V2.0 を掲載。公開フレームの CAN ペイロードは最大 8 バイトで、CAN FD 対応はこの仕様から確認できない。PC→変換器の送信系フレームは表と例の一部が一致しないため、駆動コマンドに流用しない。
- `probe_dm_usbcu1.py --usb-only` を接続先で実行。921600 baud・8N1、固定デバイスパスで、資料記載の変換器宛てハートビート `55 04 AA 55` のみを送った。ポートは開けたが 1 秒以内に受信バイトなし。ポート起動時の待機を追加した再試行でも応答なし。CAN 送信、設定変更、モーター給電なし。実機のモデルまたは FW が当該仕様と一致するかは未確認。
- 次は筐体・基板の型式／リビジョンを確認する。純正ツールがすでに使える環境がある場合は、CAN 未接続で変換器を認識するか、表示される版情報を確認する。走行用は引き続き SocketCAN 対応アダプターを候補とする。

### MKS CANable Pro V1.0 候補（USB 単体・読み取り確認）

- 接続先で `1d50:606f` (`canable.io` / `canable_gs_usb`) を検出。同じ USB インターフェースに Linux の `gs_usb` がバインドされ、`can0` が生成された。ユーザー申告の MKS 実機との対応は要確認。
- `can0` は `DOWN` / `STOPPED`、`maxmtu 16`。現構成は Classic CAN として扱う。CAN FD 対応とは見なさない。FW 書き込み、CAN リンクの起動、CAN フレーム送信は行っていない。
- [Makerbase リポジトリ](https://github.com/makerbase-mks/CANable-MKS) は Pro V1.0 と V2.0 を分けている。復旧が必要な場合のみ Pro V1.0 の資料・基板・MCU の一致と USB DFU 認識を先に確認し、V2.0 向けイメージは使わない。
- 接続中の個体が CANable であることをユーザーが確認。実機 `can0` が DOWN のとき、`can_monitor` が `SocketCAN unavailable` / `CAN interface is not UP` の ERROR を出すことを確認した。SSH からの `sudo -n` は不可。CAN 配線・駆動電源を外したまま管理者が listen-only でリンクを起動した後、診断が無通信の STALE に切り替わることを次に確認する。1 Mbit/s は USB 単体試験用の暫定値で、ドライバ実機の設定値を確認したものではない。
- USB 単体の起動試験に合格。`can0` は `UP`、`LISTEN-ONLY`、Classic CAN（MTU 16）、1 Mbit/s、sample point 0.750。ROS モニターは `socket_open: true`、`STALE: No recent CAN data frames`、`error_rx: 0`。起動前後のカウンターは RX/TX とも 0。モニターは終了し、リンクは listen-only のまま。物理 CAN の送受信は未検証。生ログ `log/stage-b-canable-listen-result.log`。

### モーター銘板と通電前の条件

- 写真で DAMIAO `DM-S3519-1EC`、定格 DC 24 V を確認。使用電源は 24 V、独立した駆動電源遮断手段は現状なし（ユーザー申告）。FW は不明。
- メーカー資料の速度指令のエンコードはオフラインの単体テストのみ。実行ノードに組み込まず、アダプター・ドライバに CAN 指令は送らない。速度ゼロを安全停止とは見なさない。
- この状態では実機への給電・駆動指令試験・床上走行には進まない。次の実機試験には、担当者がすぐ操作でき、PC・USB・CAN に依存しない 24 V 駆動電源遮断手段を先に用意する。用途に合う DC 定格と電流容量を確認し、電流制限・保護のある電源と確実な単輪固定を併せて確認する。独立遮断と通信断時の停止は別々に検証する。
- 更新：ユーザーから、電源装置と非常停止ボタンを用意したとの申告あり。ドライバ未接続で遮断時の出力消失と解除時の自動再給電なしを確認し、単輪固定・電流制限・CAN 配線と終端を確認してから初回通電に進む。現在の `can0` は DOWN。初回通電は駆動指令なし、CANable は listen-only とする。モーター返信が自発的に流れない場合、無受信だけで異常と判定しない。
- 単輪の初回通電：申告 ID `0x01`（未照合）、電源電流制限 4.5 A、非常停止で給電電圧が落ち解除だけでは再給電しないことをユーザーが確認。CANable は `1d50:606f` として再認識し、`can0` を 1 Mbit/s・listen-only で監視。ユーザー報告はドライバの赤 LED 点灯のみ。`candump` 0 行、カーネルの RX/TX・エラーカウンター 0。駆動指令・設定書き込みなし。赤 LED の意味は単独では確定できず、電流表示値・起動 UART ログ、センサー 4 ピンと三相コネクタの状態を確認する。生ログ `log/stage-b-single-power-listen.log`。

### 既存の駆動試験コードとの照合

- ユーザー報告：駆動試験は実施済み。接続先の `~/Downloads/omni_ps4.py` と `~/ダウンロード/omni_ps4.py` は同一（SHA-256 `ed55c2b97b991615e366e98837f8456f837bfff7a1e079c4ee54ef3235944e92`）。コードを読んだだけで実行・変更はしていない。
- 既存コードは USB シリアル（既定 `/dev/ttyACM0`、921600 baud）から変換器へ転送を要求する。ROS の候補である CANable/SocketCAN とはトランスポートが別。駆動速度は `0x200 + ID`、32-bit リトルエンディアン float の出力軸 rad/s を先頭に入れ、後ろ 4 バイトをゼロで埋めた DLC 8。メーカー資料の例は DLC 4。実機で動いた DLC 8 を SocketCAN 側の互換候補とし、ID `0x01` の単輪ベンチで確認する。USB 側の応答がなくても CAN 転送が動く可能性があるので、変換器ハートビートの不応答だけでは非互換と判定しない。
- コード上の車輪割り当ては `1=右前、2=右後、3=左後、4=左前`（実機照合は別途）。L1 解放時のゼロ指令と駆動無効化があるが、CAN 返信は解析せず破棄する。プロセス強制終了、USB/CAN 断、PC 停止時の駆動側ローカル停止はこのコードからは確認できない。設定上の上限値と引数エラーメッセージの範囲も一致しないため、既存コードをそのまま ROS から実行・流用しない。
- 既存の駆動確認は DAMIAO 純正 USB-CAN 経由だったとの申告。現 CANable 構成での赤 LED の意味と動作は未確認。listen-only の監視は 300 秒で終了（exit 124）。次に単輪 ID `0x01` へメーカー資料の CAN パラメータ読み出し（標準 ID `0x7FF`、操作 `0x33`）だけを送り、`sw_ver`（RID `0x0E`）の応答でリンクを確認する。応答がなければ駆動・設定書き込み・ビットレート総当たりには進まない。応答に成功した場合に `CTRL_MODE` と通信設定の読み出しへ進む。
- CANable 通常モードの 1 Mbit/s で ID `0x01` 宛て FW 読み出しをアプリから 1 回送信。ACK がなく CAN コントローラーが再送し `ERROR-PASSIVE`。有効な返信なし。駆動・設定書き込みはなし。ログ `log/stage-b-single-fw-read.log`。その後 `can0` が `DOWN` / `STOPPED` になったことを確認した。
- ユーザーに CAN ピン割り当ての異なるファームウェアを書いた可能性の記憶あり。Makerbase 公開の Pro V1.0 回路図は STM32F072C8Tx、CAN_RX=PB8 / CAN_TX=PB9、ADM3053。USB/gs_usb の列挙だけでは CAN ピンが正しいと確認できない。Makerbase の V1.0 candleLight 配布 ZIP は Pro と明示されていない。書き込み前に基板・MCU の印字と ROM DFU での列挙を確認し、対応イメージと現状を退避できるかを確認する。V2.0 向けは使わない。
- 基板写真で Makerbase `MKS CANable Pro V1.0` 印字、独立した 2 ピン `BOOT`、`GND/CAN_H/CAN_L` を確認。USB 単体で ROM DFU `0483:df11` に入った。管理者で現行内蔵フラッシュ 65536 バイトを退避済み：`log/canable-dfu.Pfq8aS/canable-before.bin`、SHA-256 `8069e81ce02646f19928337ee7c3619e1c386468a9e1a7d4519cb4a20506dafe`。
- [Makerbase の V1.0 配布 ZIP](https://github.com/makerbase-mks/CANable-MKS/tree/b5c7a39f049d19f62d5897a231bfcc6c34591afb/Firmware/CANable%20V1.0) 内の HEX と、Macrobase-tech/MKS-CANable `239e63ae50ba636b35cb5913c5b1943a2c9a7ab5` の Pro 名義 HEX の内蔵フラッシュ領域は完全一致。HEX の領域外レコードは切り捨て、`0x08000000..0x0800FFFF` のみの `makerbase-v1-flash-only.bin` を生成。SHA-256 `db1ec08dfb95f3f89ca743b4eda66429e53b97c256256bf312d00f60fa48ce22`。現行バックアップとは異なる。オプションバイトの変更や全領域一括消去は行わない。書き込み後に DFU で同範囲を再読出しして比較し、それから BOOT ジャンパーを外して USB 通常起動を確認する。
- ユーザーが DFU 書き込み後に読み戻し、SHA-256 と `cmp` で `canable-after.bin` と `makerbase-v1-flash-only.bin` の完全一致を SSH 側でも確認。BOOT ジャンパー解除後に `1d50:606f` / `gs_usb` / `can0` が復帰。検証直後のリンクは DOWN、RX/TX 0。以前の ACK 不成立時にハードウェアが再送を続けたため、次の同条件試験では one-shot を先に確認し、非対応なら通常送信へ自動で切り替えない。

- 配線確認後の再試験で、CANable `ONE-SHOT` / 1 Mbit/s から ID `0x01` に FW 読み出しを一度送信。CAN ID `0x000` から `01 00 33 0E 36 36 32 30` が約 0.5 ms で届き、対象 ID・読出し操作・RID と一致。FW 値は生値 `0x30323636`。直前に ACK エラー `0x20000004` も記録されたため、往復でデータが届いたことは確認したが、リンクの安定性は未確認。設定変更・駆動指令なし。ログ `log/stage-b-fw-retry-after-wiring.log`。

## 通信断時の駆動側自力停止の実測（2026-11-20）

- 専用試験 `comm_loss_stop_test.py`：別プロセスの送信者が ID 0x01 に +0.2 rad/s を送信し続け、3秒時点で SIGKILL で消滅（PC停止の模擬）。8秒時に独立ストッパーが無効化指令を送り、その最初の応答が `state=0 speed=+0.147 rad/s`。**送信消失後5秒以上、モーターは前回速度を維持し続けた**。操作者の目視でも「回り続けてから停止」を確認。
- 結論：`TIMEOUT=0` は通信ウォッチドッグなし。PC/プロセス/USBの異常時、モーターは自力で止まらない。計画の「駆動側が自力で停止」は**不成立**。手動非常停止のみが最終保険。
- 対応として PC 内の独立監視プロセス（UDPハートビート、途絶で全台ゼロ・無効化を継続送信）を追加する。プロセス異常は約0.5秒で停止できるが、**PC自体の停止・USB-CANの物理断には効かない**。この制約は床上試験の条件として明記する。ログ `log/comm-loss-stopper.log`。

## ハートビートウォッチドッグの実機検証（2026-11-20、浮上）

- `watchdog_stop.py`：駆動ベンチから UDP(127.0.0.1:55901) のハートビートを受ける独立プロセス。0.5秒以上途絶で全台へゼロ・無効化のバーストを0.5秒間隔で継続送信してラッチ。`done` 受信で正常終了。
- ベンチ統合：`bench_ds4_four` は主ループ毎にハートビート送信、静止確認・停止処理の反復内でも送信。学んだ注意：**再許可は「両スティック中立でL1解放→押下」**。スティック倒したままのL1再押下では許可は復帰しない（計画の中立再許可条件どおり）。ウォッチドッグ検証のためこのベンチの許可のみ3秒→10秒に拡大。
- 強制終了試験（SIGKILL、7回目で成功）：40秒間に5回の許可・走行・停止サイクルを確認し、**5回目の走行中（車輪指令0.176 rad/s）にベンチを強制終了**。ウォッチドッグは **+39.893秒でハートビート喪失を検知し即座に停止バースト送信**、以後0.5秒間隔で継続。誤検知なし（40秒間正常ハートビート）。操作者の物理停止観察は確認待ち。ログ `log/watchdog-bench7.log`、`log/watchdog-verify7.log`。
- 途中で判明した障害：DS4/IMUがUSBハブごと脱落していた期間があった。`ros2 topic info`の発行者数はトピック広告だけで実データを保証しないため、以降は`ros2 topic echo --once`での実データ確認を必須にした。
- この保護はPC内プロセス異常のみ有効。PC自体の死亡・USB-CAN物理断は対象外で、手動非常停止が最終保険。

- 操作者目視確認：5回目の走行中にベンチを強制終止した際、**車輪は約0.5〜1秒で自力停止した**（ウォッチドッグ停止バーストによる）。プロセス異常に対する停止経路を実機で検証済み。PC全体の死亡・USB-CAN物理断は引き続き手動非常停止のみが対策。

## 継続手動走行モードと入力途絶の真因（2026-11-20）

- `manual_drive.py`：時間枠・許可自動失効を廃止した継続運転モード。安全構成は L1 デッドマン、中立再許可、ウォッチドッグ常駐、車輪上限 0.5 rad/s、ウォッチドッグ検証時のみ許可 10 秒に拡大（base 3 秒は維持）。L1 の 1フレーム瞬断を 100 ms の猶予で吸収（武装中のみ、実解除は 100-150ms で停止）。
- 現象「押し続けても勝手に停止」：`ros2 run` で起動した joy ノード名が `game_controller_node` となり、`game_controller:` セクションのパラメータが一切適用されず `autorepeat_rate` がデフォルト 0 になっていた。DS4 が idle 報文を止めるたび `/joy` が 150ms 以上途絶し安全停止していた。`-r __node:=game_controller` で名前を合わせ解決。修正後 30 秒の未操作記録で 163Hz・gap 0件。launch 経由（Node 名指定あり）では最初から問題なし。USB ハブは無関係だった（WiFiドングルのハブ移設は不要）。
- 継続モードでの使用手順：watchdog_stop.py を常駐させ、`manual_drive.py --execute-powered-robot-estop-ready` を起動。終了は SIGINT（`done` ハンドシェイクでウォッチドッグも正常終了）。SIGKILL での終了はウォッチドッグ停止バーストを招く。
